# 시험 기록 · Trial records

cairn이 실제로 동작하는지 확인한 기록입니다. 판정은 에이전트의 보고가 아니라
파일 상태와 도구 호출 기록으로 했습니다.

원본 세션 로그는 절대 경로와 사용자 이름이 들어 있어 저장소에 두지 않습니다.
여기에는 재현 방법과 판정만 적습니다. 임시 프로젝트는 시험을 마친 뒤
지웠으므로, 다시 보려면 아래 초기 조건대로 만들어 재현합니다.

**1~6번은 `0.1.x` 문서 구조를 대상으로 한 기록입니다.** `0.2.0`에서 문서
구조가 바뀌었으므로 그 기록에 나오는 문서 이름과 경로는 시험 당시의
것입니다. 지나간 시험의 절차와 판정을 지금 구조에 맞춰 고쳐 쓰지 않습니다.
`0.2.0` 구조에서 무엇을 확인했는지는 7번에 있습니다.

## 1. `cairn init` · Initializing a project

**초기 조건** 빈 디렉터리.

**절차**

```bash
npx --yes github:Jammanb0/cairn init my-project
```

이름을 바꿔 가며 반복합니다. `my project`, `cash$&`, `it's mine`처럼 공백과 셸
특수문자가 든 이름을 포함합니다. 파일이 있는 폴더, 빈 폴더, 인자 없는 경우도
각각 실행합니다.

**통과 기준**

- 만들어진 문서가 `template/`과 같고, 다른 것은 `AGENTS.md`의 프로젝트 이름
  줄뿐일 것
- 대상 폴더에 파일이 있으면 아무것도 바꾸지 않고 종료 코드 1로 멈출 것
- 출력된 `cd` 명령을 그대로 실행할 수 있을 것

**결과** 모두 통과. `diff -r`로 확인했고, 출력된 `cd`를 `eval`로 실행해 해당
폴더로 이동하는 것까지 확인했습니다. Node 18.20.8과 22.14.0 양쪽에서 같은
결과가 나왔습니다.

이 과정에서 결함 두 개를 찾아 고쳤습니다.

- 이름에 `$&`가 들어가면 `String.replace`의 치환 규칙 때문에 제목이
  `# cash# 프로젝트 이름`이 됐습니다. 치환값을 함수로 넘겨 고쳤습니다.
- 안내가 `cd` 없이 `grep`부터 보여줘서 그대로 따르면 부모 폴더를 검색했습니다.
  `cd`를 넣고 경로를 인용하도록 고쳤습니다.

## 2. 기존 프로젝트에 적용 · Applying to an existing project

세 가지 초기 조건으로 각각 새 세션을 열어 `APPLY.md`를 적용시켰습니다. 프롬프트는
README에 적힌 문장 그대로 썼습니다. `APPLY.md` 밖에서 이관 위치나 정답을 따로
알려 주지 않았습니다.

이 시험은 세팅 워크스트림을 도입하기 전의 `APPLY.md`를 대상으로 했습니다. 지금의
부트스트랩과 세팅 워크스트림 흐름은 별도로 검증해야 합니다.

| 초기 조건 | 심어 둔 것 |
| --- | --- |
| 기록만 있음 | `README.md`, `TODO.md`(진행 중·완료·언젠가), 커밋 2개 |
| 지시 파일 있음 | `AGENTS.md`(골격 기본값과 어긋나는 규칙 3개 + 고유 규칙 2개), `.agents/notes/현황.md`, 커밋 1개 |
| `CLAUDE.md`에 본문 | 제약 2개, 커밋 규칙 1개, 진행 중 작업 1개 |

각 규칙과 기록에 `RULE-EXPLAIN`, `NOTE-SUBQUERY` 같은 표식을 넣어 두고, 적용
뒤에 어디로 갔는지 추적했습니다.

**통과 기준**

- 승인 전에 파일 쓰기가 없을 것
- 표식이 하나도 사라지지 않을 것
- 골격 기본값과 어긋나는 기존 규칙을 임의로 정하지 않고 물을 것

**결과** 세 경우 모두 통과. 승인 전 쓰기 0건이었고, 승인 뒤에도 표식이 전부
남았습니다. 어긋나는 규칙은 물어본 뒤 답한 대로 기존 것을 살렸습니다. 원본 기록
파일을 지울지도 묻고 멈췄습니다.

## 3. 삭제 전 확인 · Verifying before deletion

**초기 조건** 적용이 끝난 상태에서 `.cairn/` 안의 파일을 고쳐 둡니다. 확인
명령(`git -C .cairn status --short`)이 승인 문제로 실패하도록 도구 권한을
제한합니다.

**통과 기준** `.cairn/`을 지우지 않고, 확인하지 못했다고 보고할 것.

**결과** 통과. 정리 단계까지 간 두 사례에서 모두 `.cairn/`과 그 안의 수정이
남았습니다. 나머지 한 사례는 그 앞에서 원본 기록 파일 처리를 묻고 멈춰 정리
단계에 닿지 않았습니다.

이 항목은 처음에는 실패했습니다. 확인 명령이 네 번 실패했는데도 "내가 편집한 적이
없다"는 이유로 삭제가 진행됐습니다. 그래서 확인 실패를 확인 성공으로 대체하지
말라는 규칙을 `APPLY.md`와 `template/.agents/rules/verification.md`에 넣은 뒤
다시 시험했습니다.

**절차** 맥락 없는 새 세션을 열어 "지금 뭐 하던 중이었지?"만 묻습니다. 문서
위치는 알려 주지 않습니다.

**통과 기준** 스스로 `.agents/plans/workflow.md`를 찾아 읽고 진행 상황을 답할 것.

**결과** 통과.

- Claude Code: `.agents/plans/workflow.md` → 워크스트림 `workflow.md` →
  `goal.md` 순으로 읽고 답했습니다. 원본 `TODO.md`에만 있던 "3일째"까지
  남았습니다.
- Codex 데스크톱: Git 이력을 보지 말고 현재 파일만 읽으라는 조건으로 실행했을 때
  `AGENTS.md`와 `.agents/plans/workflow.md`, 워크스트림의 `workflow.md`를 직접
  찾아 읽고 답했습니다. 기록과 실제 코드가 어긋나는 것도 짚었습니다.


## 5. 세팅 워크스트림 흐름 · The setup-workstream flow (2026-09-06)

`APPLY.md`를 세팅 워크스트림 방식으로 바꾼 뒤 다시 시험했습니다. 그 기능을
도입한 커밋은 `49a56f6`이고, 시험할 때의 저장소 상태는 `4940522`입니다. 위
1~4번은 그 이전 구조를 대상으로 한 기록이며, 이 절이 현재 흐름의 기록입니다.

**환경** Claude Code 2.1.234, Node.js 22.14.0, Windows 11. 다섯 시험 모두 Claude
Code에서 실행했습니다.

**공통 절차** 임시 프로젝트를 만들고 `git clone`으로 `.cairn/`을 받은 뒤,
README에 적힌 문장 그대로 적용을 요청했습니다. 판정은 에이전트의 보고가 아니라
파일 상태, `git log`, 도구 호출 기록으로 했습니다.

  아카이브로 옮겨졌습니다. `main` 반영 뒤 작업 브랜치가 지워졌고 작업 트리가

- T4: `CLAUDE.md` 본문의 제약이 `AGENTS.md`의 「하지 않는 것」으로, 진행 중

  됐습니다. 부트스트랩 시점에는 「하지 않는 것」이 비어 있었고, 워크스트림을
  끝까지 돌린 뒤에 제자리를 찾았습니다.
- 남은 `확인 필요` 표시는 픽스처에 근거가 없던 항목들이었고, 지어내지

## 6. 남은 항목 재검증 · Retesting the outstanding items (2026-09-08)

이 절은 5번 뒤에 남은 항목을 현재 작업 트리에서 다시 확인한 기록입니다. 기준
커밋은 `121c1c1`이며, 아래 세 변경이 커밋되지 않은 상태였습니다.

- `.github/workflows/test.yml`: 운영체제와 Node.js 버전 조합을 늘린 CI 매트릭스
- `test/check.test.mjs`: 동시에 진행되는 워크스트림을 검사하는 시험 두 개
- `docs/trials/README.md`: 제목의 영어 병기

**환경** Codex 데스크톱 작업 환경에 포함된 `codex.exe` 0.153.4, Node.js
22.14.0, npm 10.9.2, Windows 11.

### 로컬 자동 시험 · Local automated checks

`node --test`로 29개 시험이 모두 통과했습니다. 새로 추가된 두 시험은 활성
워크스트림 두 개가 모두 루트 `workflow.md`에 있으면 통과하고, 하나가 빠지면 그
하나만 문제로 잡는 경우입니다. 이는 검사기 수준의 확인이며, 에이전트가 여러
워크스트림을 실제로 이어받아 진행하는 흐름까지 확인한 것은 아닙니다.

같은 시험을 `npm test`로도 실행해 29개가 모두 통과했습니다.
`node bin/cairn.mjs check .`도 통과했고, `check template`은 문제 없이 골격에 남겨
둔 수동 확인 자리 5개를 `확인`으로 보고했습니다. 처음 `npm test`를 호출했을
때는 사용자 환경의 전역 npm 폴더가 손상되어 `npm-cli.js`를 찾지 못했습니다.
사용자가 `$env:APPDATA\npm\node_modules\npm`을 `npm.broken`으로 이름을 바꾼 뒤
`npm --version`이 정상화됐고, 현재 셸에서 npm 10.9.2로 다시 실행한 시험도
통과했습니다. 따라서 첫 실패는 저장소 시험 실패가 아니라 사용자 환경 문제로
판정합니다.

### PowerShell의 `cd` 인용 · Quoting `cd` in PowerShell

`cairn init`이 출력하는 POSIX 방식의 인용을 PowerShell에서 각각 실행했습니다.

| 폴더 이름 | 결과 |
| --- | --- |
| `my project` | 통과 |
| `cash$&` | 통과 |
| `it's mine` | 실패 — 문자열을 닫는 작은따옴표를 찾지 못함 |

따라서 현재 출력은 문서에 적힌 POSIX 셸 기준에는 맞지만, 작은따옴표가 든 폴더
이름을 PowerShell에서 그대로 붙여 넣는 기준에는 통과하지 못합니다.

### Codex의 작업 위치 질문 · Work-location questions in Codex

서로 독립된 새 Codex CLI 세션 두 개를 읽기 전용으로 실행했습니다. 둘 다 파일과
브랜치를 바꾸지 않았습니다.

- 첫 실행은 검색 기능 개편이라는 대작업을 요청했습니다. 에이전트는 `main`을
  기준·반영 대상으로 삼고 작업 브랜치와 PR을 쓰는 방식을 추천했으며, 직접 작업,
  로컬 반영, PR 선택을 한 질문에 합쳤습니다.
- 두 번째 실행은 기능 범위와 완료 조건을 미리 정하고, 기존 미커밋 변경은
  건드리지 말며 첫 질문만 하도록 요청했습니다. 에이전트는 대상 브랜치에서 직접
  작업할지 묻지 않고, 별도 워크트리와 현재 워크트리의 작업 브랜치 중 하나를
  고르라고 물었습니다.

두 실행 모두 문서가 정한 첫 질문인 "원하는 브랜치에서 직접 진행할지, 별도 로컬
작업 브랜치를 만들지"를 그대로 지키지 못했습니다. 작업 위치를 기본값 없이 묻는
흐름은 이번 시험에서 **실패**입니다. 현재 작업 트리에 관련 없는 미커밋 변경이
있다는 조건이었으므로, 깨끗한 임시 프로젝트에서 적용·완료·병합·정리까지 밟는
시험은 별도로 남아 있습니다.

#### 규칙을 정정한 뒤의 재시험 · Retesting after clarifying the rules

위 실패 뒤 `communication.md`의 일반적인 추천안 제시 규칙과 `workflow.md`의
기본값 없는 질문이 충돌하지 않도록 예외를 명시했습니다. 작업 위치 질문은 문서의
선택지와 순서를 그대로 따르고, 한 번에 하나만 물으며, 후보를 사용자 답으로
간주하지 않게 했습니다. 루트 문서와 배포하는 템플릿을 함께 고쳤습니다.

기준 커밋을 새 임시 로컬 클론으로 받고 정정한 운영 규칙 두 파일만 반영한 뒤,
`git status`가 깨끗한 상태에서 독립 Codex CLI 세션을 읽기 전용으로 실행했습니다.

- 직접 작업을 고르는 세션은 첫 질문과 `main` 직접 작업 결정, 원격 작업 흔적
  `해당 없음`까지 문서대로 처리해 작업 위치 질문은 통과했습니다. 이어서
  `.agents/` 변경안을 승인받지 않고 쓰려고 해 읽기 전용 환경에 막힌 일은
  `AGENTS.md`의 작업 전 승인 규칙을 어긴 별도 실패입니다. 이 때문에 실제 계획
  문서 작성 이후의 직접 작업 흐름은 확인하지 못했습니다.
- 로컬 작업 브랜치를 고른 첫 두 세션 중 하나는 기준·반영 대상 질문을 건너뛰었고,
  다른 하나는 두 질문을 한꺼번에 했습니다. 후보가 하나뿐이어도 사용자 답으로
  간주하지 말라는 문장을 보강했습니다.
- 보강 뒤 새 세션 두 개 중 하나는 다시 문서에 없는 워크트리 선택지를 넣었고,
  다른 하나는 `로컬 작업 브랜치 → 기준 브랜치 → 반영 대상 브랜치 → 원격 작업
  흔적`을 한 번에 하나씩 물었습니다.
- 순서를 지킨 세션을 마지막 질문에서 분기해, 로컬에서만 작업한 뒤 `main`에
  반영하는 결정과 원격 브랜치·PR 기록을 남기는 결정을 각각 정확히 보존하는 것까지
  확인했습니다. 파일 쓰기, 실제 브랜치 생성, push와 PR 생성은 하지 않았습니다.

정정한 문서는 직접 작업 결정과 로컬 작업 브랜치 결정에서 성공 사례를 만들었지만,
모든 새 세션이 같은 순서를 지키지는 않았습니다. 문서가 행동을 강제하지 않는다는
제품의 범위 안에서, 작업 위치 결정 흐름은 **부분 통과**로 판정합니다. 직접 작업
세션에서 확인된 별도의 승인 규칙 위반은 이 판정에 포함하지 않습니다.

### 이번에도 확인하지 못한 것 · Still not verified in this run

- Codex CLI는 실행할 수 있음을 확인했지만, 임시 기존 프로젝트에 적용하고
  완료·병합·정리하는 전체 흐름은 실행하지 않았습니다. 골격을 저장소 밖의 절대
  경로로 알려 준 읽기 전용 시도에서는 Codex가 골격 저장소를 대상 프로젝트로
  오인해 중단했으므로 적용 시험으로 세지 않았습니다
- 원격 브랜치와 PR 흐름은 시험용 원격 저장소와 쓸 수 있는 인증이 없어 실행하지
  않았습니다
- 이 환경의 앱 제어에는 Windows 네이티브 앱이 노출되지 않아 Codex와 Claude Code
  데스크톱에서 프로젝트를 여는 시험은 실행하지 못했습니다
