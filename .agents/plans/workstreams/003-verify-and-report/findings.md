# 검증과 시험 기록 개편 — 발견

> 시험에서 나온 것을 판정과 근거로 남깁니다. 판정은 에이전트의 보고가 아니라
> 파일 상태와 명령 출력으로 했습니다. 최종 정리는 `docs/trials/README.md`로
> 갑니다.

## 시험 조건

임시 기존 프로젝트 `logmill`을 저장소 밖에 만들었습니다. `AGENTS.md`(제약 2개 +
영어 커밋 규칙 + 검증 명령), `TODO.md`(진행 중·완료·언젠가), 코드 한 파일, 커밋
하나. 각 항목에 표식을 붙여 이관 뒤 추적했습니다. 커밋 규칙은 일부러 골격
기본값(한국어)과 어긋나게 두었습니다.

적용은 이 세션이 하지 않고 맥락 없는 별도 에이전트에 맡겼습니다. README에 적힌
사용자 문장만 주고, 사용자가 이미 정했을 것(브랜치, `.agents/` 커밋)만 미리
답으로 넣었습니다. 어긋나는 커밋 규칙은 답을 주지 않았습니다.

## 2단계 — 기존 프로젝트에 적용

### 통과

| 항목 | 근거 |
| --- | --- |
| 표식 7개 전부 보존 | `grep -rl`로 각 표식이 옮겨진 자리 확인. 원본 `TODO.md`도 그대로 |
| 어긋나는 규칙을 덮어쓰지 않음 | `RULE-COMMIT-EN`이 살아남아 커밋 4개가 실제로 영어로 작성됨 |
| 적용 뒤 검사기 통과 | 픽스처에서 `check .` 종료 코드 0, 문제 0 |
| 허락 없이 아카이브하지 않음 | `.agents/archive/` 폴더 자체가 생기지 않음. 세팅 워크스트림을 활성으로 두고 승인 대기로 갱신 |
| 단순한 작업에 `plan.md`를 만들지 않음 | `002-streaming-parser/`에 `README.md`와 `status.md`뿐 |
| 골격 저장소를 건드리지 않음 | 이 저장소 파일 47개, 작업 트리 깨끗, 마지막 커밋이 이 세션 것 |

`plan.md` 미생성은 특히 의미가 있습니다. 그 에이전트에게 생성 기준을 알려 준 적이
없습니다. 문서를 읽고 스스로 판단했습니다.

### 실패

**한 번에 끝내야 하는 실행 조건에서 「승인 전에 쓰지 않는다」를 지키지
못했습니다.** `APPLY.md`는 승인 전 파일 쓰기를 금지하고, 사용자 문장에도 변경안을
먼저 보여 달라는 요구가 있었습니다. 되물을 수 없는 조건이라 먼저 쓰고 나중에
보고했습니다.

**이것은 시험 설계의 한계이기도 합니다.** 별도 에이전트는 되물을 수 없습니다.
실제 대화형 세션에서 같은 결과가 난다는 뜻이 아닙니다. 0.1.x 시험(2번, 5번)에서는
대화형 세션이 승인 전 쓰기 0건이었습니다.

## 문서에서 나온 모순

### 1. 골격 정리 절차가 살아 있는 저장소를 지울 수 있습니다

`APPLY.md`의 「골격 위치」 표는 형태를 셋으로 나눕니다.

```text
대상 저장소 안의 임시 클론   .gitignore 한다   정리 한다
대상 저장소 밖의 임시 클론   안 한다           정리 한다
대상 저장소 자신             안 한다           하지 않습니다
```

**저장소 밖에 있으면서 지우면 안 되는 골격이 표에 없습니다.** 이번 시험의 골격이
바로 그것입니다 — 적용하려고 받아 온 클론이 아니라 사용자가 계속 쓰는 개발
저장소입니다. 표를 기계적으로 읽으면 두 번째 줄에 걸려 정리 대상이 됩니다.

`setup-workstream/plan.md` 8단계의 안전 확인 다섯 가지도 막지 못합니다. 실제로
대조해 보니 넷이 그대로 통과합니다.

| 확인 | 이 상황에서 |
| --- | --- |
| 정리 대상으로 기록되어 있는가 | 표를 따랐다면 `예` |
| 대상 저장소 루트나 상위가 아닌가 | 아니다 → 통과 |
| 안에 `APPLY.md`·`template/`·`setup-workstream/`이 있는가 | 있다 → 통과 |
| 임시 골격 경로 참조 검사가 통과했는가 | 참조 0곳 → 통과 |
| 폴더 안의 파일을 사용자가 고친 것이 없는가 | 작업 트리 깨끗 → 통과 |

마지막 항목은 판정이 뒤집혀 있습니다. **잘 관리된 저장소일수록 더 안전해
보입니다.** 빠진 확인은 하나입니다 — 이 폴더를 이번 적용에서 내가 받아 왔는가.

시험을 맡은 에이전트는 지우지 않았습니다. 다만 그것은 프롬프트에 지우지 말라고
명시했기 때문이고, 절차만으로는 막히지 않습니다.

### 2. 진행 중 기록을 이관하면 워크스트림 생성 규칙과 부딪힙니다

`workstreams.md`는 사용자 허락 없이 워크스트림을 만들지 말라고 합니다.
`setup-workstream/plan.md` 2단계는 진행 중 기록을 워크스트림 폴더로 옮기라고
합니다. 구조상 진행 중 작업이 놓일 다른 자리가 없습니다 — `ideas.md`는 현재
문제를 두지 않는 곳이고 `history.md`는 끝난 것만 둡니다.

기록을 잃지 않으려면 만들어야 하고, 만들려면 허락이 필요합니다. 세팅 중의
워크스트림 생성을 예외로 둘지 정해야 합니다.

### 3. 원본 기록을 지울지 물을 수 없으면 어느 쪽이든 규칙을 어깁니다

`setup-workstream/plan.md` 2단계는 원본을 지울지 사람에게 물으라고 합니다.
`plans/README.md`는 같은 상태를 두 파일에 반복해서 적지 말라고 합니다. 묻지
못하면 둘 중 하나는 어깁니다.

### 4. 골격 위치의 절대 경로가 보안 규칙과 부딪힙니다

`APPLY.md`는 골격 위치의 실제 경로를 `status.md`에 적으라고 합니다. 공개
저장소에 적용하면 운영체제 사용자 이름이 그대로 들어갑니다. 이 저장소
`AGENTS.md`가 시험 기록에 절대 경로와 사용자 이름을 넣지 말라고 한 것과 같은
성격의 문제입니다.

### 5. 임시 골격 참조 검사는 기본 경로에서만 작동합니다

`lib/check.mjs`는 `.cairn` 문자열과 `.cairn/`으로 시작하는 토큰만 특별히
다룹니다. 골격을 다른 이름이나 경로에 두면 그 검사가 조용히 아무것도 하지
않습니다.

## 덤으로 확인된 것

- **검사기의 날짜 오탐이 실제로 걸립니다.** 적용 에이전트가 `current.md`에 날짜를
  적으면 `2026-09-09`의 뒷부분이 워크스트림 이름으로 잡힌다는 것을 스스로 확인하고
  피해 갔습니다. `ideas.md`에 이미 후보로 적어 둔 것과 같은 문제입니다.
- **`node --check`는 `.js` 파일에서 오탐을 냅니다.** 픽스처 코드가 문자열 리터럴
  안에 줄바꿈이 든 문법 오류인데 `node --check src/parse.js`가 종료 코드 0을
  냈습니다. 같은 내용을 `.mjs`로 바꾸면 `SyntaxError`이고 `import`도 실패합니다.
  검증 명령 자체를 믿기 전에 실제로 실패하는지 확인해야 한다는 사례입니다.
