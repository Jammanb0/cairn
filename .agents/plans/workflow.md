# 전체 작업 흐름

> 현재 이어갈 대작업과 각 대작업의 다음 행동을 찾는 단일 원본입니다.
> 세부 상태는 해당 대작업의 `workflow.md`에서 관리합니다.

## 현재 대작업

현재 진행 중인 워크스트림은 없습니다.

## 대작업 관리 흐름

**조건이 붙은 단계는 그때만 합니다.** 조건이 없는 단계는 대작업이면 항상
밟습니다.

1. 새 요청이 기존 대작업의 범위에 속하는지 확인합니다. 속하면 이 파일에 적힌
   「작업 위치」, 기준 브랜치, 반영 대상 브랜치와 원격 작업 흔적 결정을 먼저
   확인하고 그대로 따릅니다. 문서 갱신도 구현도 기록된 작업 위치에서 합니다.
   적힌 브랜치와 지금 브랜치가 같은지 먼저 확인하고, 다르면 작업
   트리에 커밋하지 않은 변경이 있는지 본 뒤 옮깁니다. 관련 없는 변경이 있거나
   어느 브랜치에 속하는지 불분명해서 안전하게 옮길 수 없으면 옮기지 말고
   사용자에게 알립니다. 적힌 브랜치가 없거나 기록과 실제가 다를 때도 임의로
   새로 만들지 말고 알립니다.
2. 속하지 않으면 대작업인지부터 봅니다. 여러 날에 걸치거나 여러 커밋으로
   나뉘고 중간에 맥락을 다시 잡아야 하는 작업만 대작업입니다.
3. **(대작업이 아닐 때)** 워크스트림을 만들지 않고 그냥 합니다. 이 파일에도 적지
   않습니다. 나중에 필요한 기록은 커밋 메시지로 남습니다.
   작은 작업으로 시작했지만 여러 날 또는 여러 커밋으로 이어지게 되면, 그
   시점에 대작업으로 승격하고 4번부터 진행합니다. 처음부터 정확히 가를 필요는
   없습니다.
4. 대작업이면 브랜치 후보와 다음 번호를 먼저 확인합니다. 현재 브랜치와
   upstream, 원격 기본 브랜치, 저장소 문서와 기존 관례, 특정 개발·릴리스
   브랜치를 대상으로 하는 작업인지를 봅니다. `main`이라고 가정하거나 시작점과
   반영 대상이 같다고 가정하지 않습니다. 이 단계에서는 아직 작업 위치를 정하지
   않습니다. 근거가 부족하거나 후보가 여럿이면 5번의 질문에 선택지를 함께
   보여줍니다.
5. 작업 위치에는 기본값을 두지 않고 아래 순서로 사용자에게 묻습니다. 이
   결정을 계획 문서에 담아야 하므로 문서를 만들기 전에 물어봅니다.

   먼저 어디서 작업할지 묻습니다.

   > 이 대작업을 원하는 브랜치에서 직접 진행할까요, 아니면 별도의
   > `workstream/<번호>-<이름>` 로컬 브랜치를 만들어 진행할까요?

   직접 작업을 고르면 어느 브랜치인지 확인합니다. 그 브랜치가 기준 브랜치이자
   반영 대상 브랜치입니다.

   로컬 작업 브랜치를 고르면 기준 브랜치와 반영 대상 브랜치를 각각 확인한 다음,
   원격 작업 흔적을 물어봅니다.

   > 작업 브랜치를 원격에 올리고 PR 기록을 남길까요, 아니면 로컬에서만 작업한
   > 뒤 대상 브랜치에 반영할까요?

   흔적을 남기지 않아도 최종 커밋은 대상 브랜치에 남습니다. 남기지 않는 것은
   원격 작업 브랜치, PR, 병합 커밋과 작업 브랜치 이름입니다.
6. 기준 브랜치에서 `workstreams/<번호>-<이름>/`을 만들고 `README.md`와
   `workflow.md`로 범위와 완료 조건을 정합니다. 이 파일의 「현재 대작업」에
   문서 위치, 작업 위치, 기준 브랜치, 반영 대상 브랜치와 원격 작업 흔적 여부를
   함께 적습니다. 대상 브랜치에서 직접 작업하면 원격 작업 흔적은 `해당 없음`입니다.
7. 여기까지를 기준 브랜치에 커밋합니다. 계획을 기준 브랜치에 두는 이유는
   나중에 시작하는 다른 세션이 무엇이 진행 중이고 어디서 작업하는지 볼 수 있게
   하기 위해서입니다. 작업 위치와 브랜치·원격 흔적 결정이 이 커밋에 들어가야
   그게 성립합니다. 같은
   저장소에서 기준 브랜치를 읽는 세션에만 보이며, 다른 기기나 원격 환경에서도
   보이게 하려면 이 커밋을 push해야 합니다.
   `.agents/`를 커밋하지 않는 프로젝트라면 이 커밋이 만들어지지 않습니다. 계획은
   이 작업 공간에만 남고 다른 checkout에서는 보이지 않으므로, 이어받을 방법을
   사용자와 정해 둡니다.
8. **(작업 브랜치를 만들기로 했을 때)** `workstream/<번호>-<이름>`을 만들고 실제
   구현은 그 브랜치에서 합니다. 7번에서 계획 커밋을 만들었으면 그 커밋에서
   가릅니다. `.agents/`를 커밋하지 않아 계획 커밋이 없으면 기준 브랜치의
   현재 `HEAD`에서 가르고, 계획 문서는 추적되지 않은 채 작업 트리에 그대로
   남습니다. 반영 대상 브랜치에서 직접 하기로 했으면 브랜치를 만들지 않고 그대로
   진행합니다.
9. **(필요할 때만)** 상세 설계는 `design.md`, 따로 보존할 긴 결정 근거는
   `decisions.md`에 둡니다.
10. 작업이 끝나면 실제 Git 상태를 다시 확인하고, 시작할 때 기록한 반영 대상과
    원격 작업 흔적 결정을 따릅니다. 같은 선택을 다시 묻지 않습니다. 저장소 상태가
    달라졌거나 사용자가 방향을 바꾸면 새 결정을 문서에 갱신합니다. fast-forward,
    rebase, squash 중 무엇을 쓸지는 묻지 않고, 기록된 결과를 안전하게 만드는
    절차를 스스로 판단합니다. 반영 대상 브랜치에서 직접 했다면 별도 반영 단계가
    없습니다.
11. `history.md`를 갱신하고 워크스트림 폴더를 `.agents/archive/workstreams/`로
    옮깁니다. 결과는 완료일 수도 취소일 수도 있습니다.
12. 최종 상태를 지금의 작업 위치에서 커밋합니다. 커밋은 `AGENTS.md`의 승인
    규칙을 따릅니다. 이미 커밋한 구현과 새로 만든 이력·아카이브가 빠짐없이
    들어갔는지 확인합니다.
    `.agents/`를 커밋하지 않는 프로젝트라면 추적되는 변경만 커밋에 들어갑니다.
    이력과 아카이브는 로컬에만 남으므로, 잃지 않게 백업할지 사용자에게
    확인합니다.
13. **(작업 브랜치를 썼을 때)** 고른 방식에 따라 대상 브랜치에 반영하고, 필요하면
    원격에 푸시하거나 PR을 병합합니다.
14. 구현 결과가 대상 위치에 들어갔는지 확인합니다. 이력과 아카이브는
    `.agents/`를 커밋하는 프로젝트라면 같은 자리에서, 커밋하지 않는
    프로젝트라면 현재 로컬 작업 공간에서 확인합니다.
15. **(작업 브랜치를 썼을 때)** 확인이 끝난 뒤에 지웁니다.

커밋과 `git push`, PR 생성 승인 규칙은 `AGENTS.md`를 따릅니다. 브랜치를 만드는
것만 승인 없이 합니다.

현재 문제와 외부 상태를 기다리는 항목은 관련 워크스트림의 `workflow.md`에
둡니다. 아직 착수를 약속하지 않은 기능과 선택적 개선만 `ideas.md`에 둡니다.

## 대작업을 반영할 때

작업 브랜치를 써서 진행한 경우에 해당합니다. 반영 대상 브랜치에서 직접 했다면
결과가 이미 그 브랜치에 있으므로 반영 단계가 없고, push 여부만 기존 승인 규칙을
따릅니다.

**흔적을 남기지 않기로 한 경우.** 변경을 숨긴다는 뜻이 아닙니다. 최종 커밋과
앞서 만든 계획 커밋은 대상 브랜치에 남습니다. 계획 커밋은 `.agents/`를 커밋하는
프로젝트에 해당하고, 커밋하지 않는 프로젝트의 계획과 이력은 로컬 작업 공간에만
남습니다. 남기지 않는 것은 원격 작업 브랜치, PR, 병합 커밋, 그리고 작업 브랜치
이름이 원격 이력에 드러나는 것입니다.
저장소 상태를 보고 필요한 것을 골라서 합니다 — 대상 브랜치 최신화, 필요하면
작업 브랜치 rebase, fast-forward가 맞으면 fast-forward, 중간 커밋 정리가
필요하면 squash, 직접 푸시가 맞으면 그 방식. 반영 뒤 로컬 대상 브랜치를
최신화합니다. 한 가지 방식을 무조건 쓰지 않습니다.

**흔적을 남기기로 한 경우.** 로컬 작업 브랜치를 원격에 만들고 PR을 연 뒤,
사용자가 고른 대상 브랜치로 저장소 정책에 맞는 방식으로 병합합니다. 끝나면
원격과 로컬 작업 브랜치를 정리합니다.

**취소하는 경우.** 기록은 남기고 구현은 남기지 않습니다.

- 미완성 구현은 대상 브랜치에 반영하지 않습니다.
- 취소 이유와 당시 상태, 결정 기록만 `history.md`와 아카이브에 남깁니다.
- 기록이 대상 브랜치에 안전하게 들어간 것을 확인한 뒤에 로컬 작업 브랜치를
  지웁니다.
- 살려야 할 코드가 있으면 어디까지 가져갈지 사용자가 정합니다.

구현을 빼고 기록만 옮기는 방법은 저장소 상태를 보고 판단합니다. 사용자에게 Git
명령을 고르게 하지 않습니다.

**대상 브랜치가 처음 기준 브랜치와 다른 경우.** 처음 기준 브랜치에 활성
워크스트림 기록만 덩그러니 남지 않게 함께 정리합니다. 구현 결과와 이력,
아카이브가 각각 어느 브랜치에 들어가는지 확인하고, 두 브랜치에 서로 어긋나는
상태를 남기지 않습니다.

**멈춰서 물어야 하는 경우.** 해결 방향이 분명하지 않은 충돌, 브랜치 보호나
ruleset 때문에 직접 반영이 막힌 경우, 권한 문제, 대상 브랜치를 정할 근거가
부족한 경우, 공개된 대상 브랜치의 이력을 다시 써야만 하는 경우. 공개된 대상
브랜치에 force push하지 않습니다.

완료할 때는 시작 시 선택을 다시 묻지 않습니다. 실제 Git 상태와 기록된 방향을
대조해, 실행할 구체적인 반영·push·PR 작업을 보여주고 필요한 승인을 받습니다.
기록과 현재 상태가 다르면 임의로 진행하지 말고 사용자에게 알립니다.
